# 개발 Seed 데이터

## 구현 기준

이 프로젝트는 애플리케이션 ORM이나 별도 마이그레이션 프레임워크 없이 PostgreSQL DDL과 `psql`의 `\ir` 명령으로 스키마와 데이터를 관리한다. 실행 순서는 `01_schema.sql`과 `02_seed.sql`에 고정되어 있다. PostgreSQL (버전: TODO)에서 검증했으며 `pgcrypto`, 범위형, GiST exclusion constraint, PL/pgSQL 트리거와 업무 함수를 사용한다.

**상태 변경이 있는 데이터는 모두 업무 함수(`schema/08_procedures.sql`)를 호출해 만든다.** 학생정보 변경 요청·승인·반려, 마일리지 신청·승인·반려·취소·회수·직권등록, 최초예산 확정, 지출 등록·승인·반려가 해당한다. 따라서 Seed 자체가 업무 함수의 정상 동작 근거이며, 변경 로그(`change_log`)는 함수가 정해진 형식으로 자동 기록한다. 함수가 없는 TOPCIT 점수 정정 이력과 만족도 응답만 직접 입력한다.

Seed는 기존 스키마와 업무 함수를 변경하지 않는다. 고정 코드와 자연 업무키를 먼저 조회하고, 없을 때만 추가하며, 같은 키에 다른 내용이 있으면 기존 행을 수정하지 않고 예외로 중단한다. 각 파일은 트랜잭션과 advisory lock을 사용하므로 중간 실패 시 해당 도메인의 입력 전체가 롤백된다.

삽입 순서는 다음 FK 의존 관계를 따른다.

1. 사용자·관리자·역할·권한
2. 대학·캠퍼스·학과·교수·예산항목·학기·프로그램유형·문항분류 등 기준정보
3. 학생과 학생정보 수정 요청 (함수: 요청 → 승인/반려, 요청일시 순서)
4. TOPCIT 회차·점수·마일리지 기준
5. 프로그램·마일리지 신청·첨부 (함수: 신청 → 승인/반려/취소/회수, 직권등록)
6. 사업·최초예산·지출 (함수: 예산 확정, 지출 등록 → 승인/반려)
7. 만족도 조사·문항·응답
8. 관계와 집계값 검증

검증 시나리오용으로 의도적으로 넣은 데이터:

| 데이터 | 검증 대상 |
|---|---|
| 승인 지출 없는 예산항목 (2026 간접비) | Q08 무지출 항목 잔액 = 예산, 집행률 0, 0 나누기 방지 |

| 회수 4건 | 누적 마일리지에서 제외, 로그에 원래 승인자 보존 |
| 미완료 응답 3건 (척도 1점) | Q10 완료 응답 기준을 빼면 평균이 달라짐 |

모든 이름, 전화번호, 이메일, 파일 경로는 가상 값이다. 계정 비밀번호는 `pgcrypto.crypt(..., gen_salt('bf'))`로 생성한 bcrypt 해시이며 복구 가능한 공통 비밀번호를 두지 않는다.

## 실행

빈 로컬 DB를 스키마부터 다시 만든다. `reset.sql`은 `public` 스키마를 삭제하므로 로컬 DB에서만 실행한다.

```bash
psql -d swknu_db -f reset.sql
```

이미 스키마가 있는 개발 DB에 Seed만 추가하거나 재검증한다. 일반 사용자 행과 운영 데이터는 삭제하거나 갱신하지 않는다.

```bash
psql -d swknu_db -f 02_seed.sql
```

실행 환경 변수 `seed_environment`는 지정하지 않으면 `development`로 동작한다. 데이터베이스 이름에 `prod` 또는 `production` 구분자가 있으면 실행을 거부한다.

Seed 무결성 검증만 다시 실행:

```bash
psql -d swknu_db -f tests/T12_seed_integrity.sql
```

Seed만 선택 삭제하는 스크립트는 제공하지 않는다. `change_log`가 UPDATE와 DELETE를 막는 불변 감사 로그이고 업무 이력의 임의 삭제는 설계 원칙에 어긋나기 때문이다. 완전 초기화가 필요하면 `reset.sql`을 로컬 전용 DB에서 실행한다.

## 검증 항목

`seed/08_verify.sql`은 다음 조건이 하나라도 맞지 않으면 예외를 발생시킨다.

- 학생·회차별 TOPCIT 점수의 유일성과 전 학생 다회차 이력
- 승인 상태 마일리지의 합과 `student.cumulative_mileage`의 일치
- 마일리지의 대기·승인·반려·취소·회수 상태 존재
- 승인 지출 합계가 항목별 지출한도 이하이며 잔액이 음수가 아님
- 승인 지출이 없는 예산항목이 최소 1개 존재 (06에서 검사)
- 만족도 **완료** 응답이 조사별 네 문항에 모두 답했고 문항 유형과 답변 유형이 일치함
- 변경 로그 처리자가 실제 `app_user`를 참조하며 각 도메인의 처리 이력이 존재함

## 현재 스키마에서 표현하지 못하는 범위

- `app_user.user_type`은 `STUDENT`와 `ADMIN`만 허용하고 `professor`는 독립 기준정보이므로 교수 로그인 계정과 역할 연결은 만들지 않았다.
- 예산 잔액과 누적 지출액 컬럼은 없다. 승인 상태 지출만 합산해 조회 시 계산한다.
- 만족도 조사에는 프로그램 참여자 테이블이 없어 프로그램 참여 여부와 설문 응답 자격을 DB FK로 연결할 수 없다.
- 만족도 응답은 학생·조사별 중복을 허용하는 설계다. 재응답 사례를 포함했고 통계에서는 최신 완료 응답을 선택해야 한다.
- 지출 상태에는 `CANCELLED`가 있지만 취소 업무 함수와 취소 처리자·일시 컬럼이 없어 Seed에는 취소 지출을 만들지 않았다.
- `change_log.target_id`는 여러 테이블의 문자·숫자 PK를 함께 담는 다형 참조라 대상 행에 대한 FK는 없고, 처리자만 `app_user` FK로 보장한다.
